# 3DS StreetPass Local WLAN

## Summary

Classic StreetPass is not Wi-Fi Direct, IBSS, or ordinary infrastructure association. It is a Nintendo-specific local WLAN protocol layered directly on 802.11 management frames and CCMP-encrypted data frames.

For Linux replication, the short version is:

- A passive observer only needs monitor mode and packet capture.
- A probe spoofer needs custom probe-response/vendor-IE control.
- A real peer needs raw 802.11 management frame control, CCMP key derivation, encrypted data frame handling, and CECD message compatibility.

The local NAND has not yet been decrypted far enough to inspect this console's CECD/NWM binaries. The notes below combine local dump triage with 3dbrew's CECD/NWM documentation.

## Relevant 3DS Components

- CECD owns StreetPass state, message boxes, relay integration, and StreetPass daemon commands.
- NWM owns local WLAN, infrastructure WLAN, socket integration, and the `nwm::CEC` StreetPass-facing local WLAN service.
- `nwm::CEC` exposes `SendProbeRequest` command `0x000D0082`, which sends a StreetPass probe request. Its input buffer is Nintendo vendor-tag data after the OUI type byte.
- Wi-Fi hardware is controlled by NWM through SDIO registers, with mapped Wi-Fi IO around physical `0x10122000`.
- CECD stores StreetPass application data in system save `00010026`, under `data:/CEC`, with per-title inbox/outbox message boxes.

## Discovery Frames

While StreetPass is enabled and the console is asleep, the 3DS repeatedly sends broadcast probe requests with SSID `Nintendo_3DS_continuous_scan_000`. These are active scans, not beacons, so another 3DS answers only after seeing a compatible probe.

The probe request contains normal 802.11 elements followed by a Nintendo vendor-specific IE:

- SSID IE: `Nintendo_3DS_continuous_scan_000`.
- Supported rates and channel-set elements.
- Vendor IE tag `0xdd`, OUI `00:1f:32` (Nintendo), OUI type commonly `0x01` for StreetPass probe content.
- Nintendo TLV data containing enabled StreetPass services and a rotating 8-byte StreetPass console ID.

The Nintendo tag payload is TLV-like:

- Type `0x11`, length `5 * service_count`, followed by one or more 5-byte service records.
- Each service record is effectively a low title ID plus flags. Example Mii Plaza service: `00 02 08 00 00`.
- Some service flags indicate a following 6-byte `ff ff ff ff ff ff` field.
- Type `0xf0`, length `0x08`, followed by the 8-byte StreetPass console ID.

The sleep-mode StreetPass MAC address and 8-byte console ID are not stable identity fields. They have been observed to rotate after StreetPass hits and after some settings/sleep transitions. The normal user-visible Wi-Fi MAC used for ordinary active scans is separate.

## Peer Handshake

The observed classic local peer sequence is:

1. Console A sends broadcast probe requests for `Nintendo_3DS_continuous_scan_000` with its Nintendo vendor IE.
2. Console B decides whether a hit is allowed for that peer/service set, usually rate-limited on the order of hours, and sends a probe response directly to A.
3. The probe response carries B's own Nintendo vendor IE and advertises a channel, commonly one of 1, 6, or 11 depending on region/environment.
4. Console A acknowledges at 802.11 level, then sends a vendor action frame and a directed probe request toward B.
5. B sends another probe response and the exchange transitions into CCMP-encrypted 802.11 data frames.
6. No ordinary open-system authentication/association sequence is required for the initial StreetPass management exchange.

The vendor action frame uses public/action category `0x7f` with Nintendo OUI `00:1f:32`. The initial management exchange can be spoofed enough to make a 3DS talk, but real message transfer requires the encrypted data phase.

## Data Encryption

StreetPass data frames use WPA2-style CCMP encryption, similar to other 3DS local WLAN protocols, but the key is generated by CECD/NWM rather than negotiated through a normal AP handshake.

3dbrew documents local StreetPass CCMP key generation as:

- CECD builds a 0x1c-byte hash block: host 8-byte StreetPass console ID, client 8-byte StreetPass console ID, host MAC, client MAC.
- CECD computes SHA1-HMAC over that block using a fixed retail or dev-unit HMAC string selected from environment info.
- The first 16 bytes of the HMAC become the CTR input for `PS:EncryptDecryptAes` with keytype 6.
- Encrypting an all-zero block yields the 16-byte CCMP key.

This means a Linux reimplementation cannot complete real StreetPass exchange by only cloning SSID and vendor IEs. It also needs exact peer IDs/MACs, correct retail/dev key path behavior, CCMP encapsulation, replay/PN handling, and CECD message formats.

## CECD Message Storage

StreetPass payloads are stored per title in CECD's system save:

- Root: `data:/CEC` in system save `00010026`.
- `MBoxList____`: registered/enabled StreetPass boxes.
- `<8-digit ID>/MBoxInfo____`: per-title metadata, HMAC key, timestamps, flags.
- `<8-digit ID>/InBox___/BoxInfo_____` and `OutBox__/BoxInfo_____`: inbox/outbox metadata.
- `<8-digit ID>/OutBox__/OBIndex_____`: outbox message index.
- Message files named `_<12-char ID>` contain a `0x6060` message header, optional extra headers, body, and HMAC.
- Relay/SPR slots use `0x6161` slot containers that group one title's messages.

For replication, CECD message compatibility matters only after the WLAN handshake works. A beacon/probe spoofer can ignore CECD payloads; a real peer needs to parse and generate these boxes/messages.

## Linux Replication Notes

There are three practical levels of replication on Linux:

1. Passive observer: use a monitor-mode adapter and Wireshark/tcpdump to capture probe requests, probe responses, vendor action frames, and encrypted data frames. Filter for SSID `Nintendo_3DS_continuous_scan_000`, vendor IE OUI `00:1f:32`, and action category `0x7f`.
2. Discovery/probe spoofer: use `hostapd` or raw injection to present SSID `Nintendo_3DS_continuous_scan_000` and include a captured or synthetic Nintendo vendor IE. This can trigger 3DS management-frame responses, but does not complete data exchange by itself.
3. Full peer implementation: implement the StreetPass management state machine, generate valid rotating probe/probe-response Nintendo tags, send Nintendo vendor action frames, derive the CCMP key, encrypt/decrypt 802.11 data frames, and implement enough CECD slot/message semantics to exchange title data.

The easiest Linux path is not a normal managed-mode socket. It needs hardware and driver support for monitor mode plus injection, or `hostapd` support for custom probe-response/vendor IEs. For full peer work, raw 802.11 frame injection is preferable because the implementation must control probe responses, directed probe requests, vendor action frames, addresses, channels, sequence behavior, and encrypted data frames.

A minimal lab implementation should be staged as:

1. Capture a real 3DS in sleep mode and save reference frames with radiotap metadata.
2. Decode the Nintendo vendor IE into service records and console ID.
3. Re-inject only harmless probe responses/action frames on a fixed legal channel and verify the 3DS keeps responding.
4. Implement CCMP key derivation and test it against two real-console captures where both StreetPass console IDs and MAC addresses are known.
5. Only after decryption works, implement CECD `0x6161` slot and `0x6060` message parsing/generation.

Important constraints:

- A standard Linux UDP/TCP/raw-IP socket cannot send these frames; this is layer 2 802.11 management/data work.
- Many Wi-Fi adapters/drivers cannot inject arbitrary management frames reliably, and even fewer allow custom encrypted data-frame construction without firmware interference.
- Regulatory behavior matters because a faithful implementation hops or advertises on channels 1/6/11 and emits probe/probe-response/action traffic.
- Reusing captured Nintendo IEs is useful for lab triggering but not sufficient for long-lived operation because MAC and console ID rotation affect both peer filtering and CCMP key derivation.
